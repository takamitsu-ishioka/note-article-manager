# 「Git」とは何か？

## 前の記事

「仕事」とは何か

前回、仕事を極端に単純化した。

仕事とは、

```
入力 → 関数 → 出力
```

である。

もう少し抽象化すれば、

```
系₀ → Transformer → 系₁
```

である。

つまり仕事とは、ある状態の世界を、別の状態の世界へ変換することである。

では、その「仕事」を保存したいとき、何を保存すればよいのだろうか。

---

## 何を保存するのか

たとえば、こんな仕事をしたとする。

```
DB v1
  ↓
列を追加
  ↓
DB v2
```

結果だけ保存するなら、DB v2を保存すればよい。

しかし、それでは「仕事」は保存されていない。

保存されているのは、仕事をした**結果**だけである。

仕事そのものを保存するなら、

```
DB v1
  ↓ migration_001.sql
DB v2
```

としなければならない。

重要なのは、

DB v1

でも、

DB v2

でもない。

その間にある、

migration_001.sql

である。

これが「仕事」だからだ。

---

## 状態ではなく、変化を保存する

人間はつい、状態を保存したくなる。

- 完成したファイル。
- 完成したDB。
- 設定済みのサーバー。
- 構築済みの開発環境。

しかし、状態だけ保存しても、その状態がどうやって生まれたのか分からない。

一方、

```
入力 + Transformer
```

があれば、

```
出力 = Transformer(入力)
```

なので、出力は再生成できる。

ならば、原則として保存すべきなのは出力ではない。

**出力を生成したTransformerである。**

---

# Gitとは何か？

ここまで来れば、Gitの役割はかなり単純になる。

> **Git = Transformerの履歴管理システム**

である。

「Gitはソースコードを管理するツールです」

という説明は間違ってはいない。

しかし、それではなぜソースコードをGit管理するのか説明できない。

ソースコードが特別だからではない。

ソースコードが、

```
入力 → 出力
```

を実現するTransformerだからGit管理するのである。

だからGitには、ソースコード以外にも、

- shell script
- makefile
- SQL migration
- Dockerfile
- 設定生成スクリプト
- テストコード
- デプロイスクリプト
- AIへのinstructions

などを入れる。

全部同じである。

**世界を変換する関数だからである。**

---

## では、入力は？

入力は原則としてGitの責務ではない。

たとえば、

100GBの観測データ

をGitに入れる必要はない。

それはストレージに置けばよい。

ただし、入力もまた一つの「系」である。

したがって、

巨大な入力

も、

```
小さな入力
  ↓ generator
巨大な入力
```

と分解できることがある。

たとえば巨大な開発DBを丸ごと保存する代わりに、

```
schema
+
migration
+
seed data
+
generator
```

から再生成できるなら、巨大なDBそのものを保存する必要はない。

Gitに保存すべきなのは、巨大なDBではなく、

**巨大なDBを作るためのTransformer**

である。

---

## では、出力は？

もっと簡単である。

```
入力 → Transformer → 出力
```

において、

入力とTransformerが保存されているなら、

出力は再生成できる。

だから、

> **出力は原則捨てればよい。**

もちろん、生成に3日かかるものを毎回再生成するのは馬鹿らしい。

その場合は保存してもよい。

しかし、それは情報を保存しているのではない。

**計算量を保存している。**

つまりcacheあるいはartifact (中間生成物) である。

この区別は重要である。

---

# Git管理すべきもの

以上から、Git管理すべきものをかなり機械的に決められる。

> 対象がTransformerなら、Git管理する。

ただしTransformerそのものが系外にある場合、

- Python
- PostgreSQL
- 外部API
- 生成AI

などを丸ごとGit repositoryへコピーする必要はない。

必要なのは、

**同じTransformerを再び取得できる情報**

である。

たとえば、

- requirements.txt
- package-lock.json
- Docker image digest
- API version
- compiler version

などである。

つまりGit管理すべきものは、

> **系内のTransformer + 系外のTransformerへのポインター**

である。

# なぜGUI操作が危険なのか

ここまで来ると、

> 「GUIを使うな」

というUNIX原理主義者の奇妙な宗教（笑）にも、多少まともな説明を与えられる。

GUIそのものが悪いのではない。

問題は、

```
状態A
  ↓
人間が画面を開く
  ↓
ボタンを押す
  ↓
値を入力する
  ↓
状態B
```

としたとき、

**AからBへのTransformerが消えてしまう**

ことである。

そこで、

```
状態A
  ↓ configure.sh
状態B
```

とする。

すると、

configure.sh

をGit管理できる。

**仕事そのもの**を保存できる。

## 手順書とは何か

```
「管理画面を開いてください」
「設定をクリックしてください」
「○○欄に123と入力してください」
「保存ボタンを押してください」
```

これは何だろう。

Transformerを自然言語で記述したものである。

そして、

```
自然言語のTransformer
  ↓
人間という処理系
  ↓
状態変換
```

を行っている。

だから揺らぐ（笑）。

可能なら、

```
./configure.sh
```

にしてしまったほうがいい。

こちらはTransformerそのものを保存できる。

# make build

ここで前回の記事に戻る。

repositoryに、

```
系内のTransformer
と、
系外のTransformerへのポインター
```

が全部入っているなら、

```
make build
```

で世界を再構成できるはずである。

さらに、

```
make run
```

で実行できるはずである。

つまりrepositoryとは、

**ある系を再構成するために必要な情報の集合**

と考えられる。

Git cloneして、

```
make build
make run
```

すれば同じ系が現れる。

かなり乱暴に言えば、

> repository = 世界の設計図  
> Git = その設計図の歴史

である。

---

# commitとは何か？

するとcommitも少し違って見える。

commitとは、

> 「ファイルを保存すること」

ではない。

ある時点で、

**世界をどう作るか**

という記述を確定することである。

```
commit₀
  ↓
変更
  ↓
commit₁
  ↓
変更
  ↓
commit₂
```

これは単なるファイルの履歴ではない。

「世界の作り方」の履歴である。

だからcheckoutすると過去へ戻れる。

正確には、

**過去の世界そのものへ戻っているのではない。**

過去の世界を再構成するためのTransformer群へ戻っている。

そこからbuildすれば、過去の世界を再生成できる。

---

# branchとは何か？

branchも同じである。

branchとは、

**世界の別の作り方を試すための分岐**

である。

```
main
  |
  +---- feature-A
  |
  +---- feature-B
```

状態をコピーしているのではない。

Transformerの歴史を分岐させている。

だからbranchは安い。

世界をコピーしているのではなく、

**世界の生成規則の差分を持っている**

からである。

---

# mergeとは何か？

するとmergeとは、

> 二つの世界を合体させることではない。

二つの系統で発達した、

> **世界の変換規則を合成すること**

である。

だからconflictが起きる。

同じ世界に対して、

こちらではこう変換する

あちらではこう変換する

という二つのTransformerが存在し、それらを自動的に合成できないとき、

Gitは人間に聞く。

> 「どっち？」

Gitは意味を知らないからである。

---

# なぜGitはソフトウェア開発で使われるのか

ここまで来ると順序が逆になる。

```
❌ ソフトウェア開発ではソースコードを扱う  
↓  
だからGitを使う
```

ではない。

```
⭕ ソフトウェア開発とは世界を変換する仕事である  
↓  
その変換規則を保存したい  
↓  
Transformerはテキストとして記述できる  
↓  
その履歴を管理したい  
↓  
Gitがものすごく都合がいい
```

である。

だからGitは、本質的にはソフトウェア専用の道具ではない。

仕事を、

```
入力 → Transformer → 出力
```

として外在化できるなら、

- 経理でも、
- 研究でも、
- 設計でも、
- インフラ構築でも、
- 文章制作でも、
- AIへの指示でも、

同じ考え方が使える。

# AI時代のGit

そして生成AIが登場した。

これまでは、

```
要求
  ↓
人間
  ↓
成果物
```

だった。

中央にいる「人間」というTransformerはGit管理できなかった。

しかし今は、

```
要求
  ↓
CLAUDE.md / instructions / prompt
  ↓
AI
  ↓
成果物
```

とできる。

AIそのものは系外のTransformerである。

しかし、

- どのAIを使うか
- 何を指示するか
- どんな規則に従わせるか

は保存できる。

つまり、

> **仕事のTransformerを、これまでよりはるかに広い範囲で外在化できるようになった。**

だからAI時代には、Gitの意味がむしろ大きくなる。

保存する対象がソースコードから、

> **仕事そのもの**

へ広がるからである。

---

# 結論

Gitとは何か。

> ソースコード管理システム？

もちろん、それでもいい。

しかし、もう少し一般化すると、

> **Git = Transformerの履歴管理システム**

である。

さらに言えば、

> **Git = 世界を再現するために必要な「変化」を記憶する系**

である。

だから、

- コードをGitに入れる。
- migrationをGitに入れる。
- makefileをGitに入れる。
- scriptをGitに入れる。
- instructionsをGitに入れる。

一方、

- 巨大な入力データは外に置く。
- 再生成可能な出力は捨てる。
- 生成が高価ならcacheとして保存する。

判断基準は、

> 「これはソースコードか？」

ではない。

> **「これは世界をどう変えるかを記述しているか？」**

である。

そう考えると、

「何をGit管理すべきか？」

という長年の問いへの答えは、恐ろしく短くなる。

> **Git管理すべきもの = 射**

以上（笑）。

| subcommand | command line example | 用途 | コメント |
|---|---|---|---|
| `clone` | `git clone <repository-url>` | リモートリポジトリをローカルにコピーする | 最初に1回だけ使うことが多い。引数は忘れていても困らない（笑） |
| `fetch` | `git fetch origin` | リモートリポジトリの最新情報を取得する | **作業中のファイルは変更しない**。まず「向こうがどうなったか」を持ってくる |
| `merge` | `git merge origin/<branch-name>` | 取得したリモートブランチの変更を現在のブランチへ統合する | `fetch` と分離して使うと、「取得」と「自分の世界への反映」が明確に分かれる |
| `add` | `git add .` | 変更したファイルを次のcommitの対象にする | ほとんど常に `.`（笑）。厳密には「staging areaへ追加する」 |
| `commit` | `git commit -m "説明"` | 現在の変更を履歴として確定する | **「この時点の世界の作り方」を確定する操作**と考えると分かりやすい |
| `push` | `git push` | ローカルのcommitをリモートリポジトリへ送る | upstreamが設定済みならこれだけ。だから後ろの引数を忘れても困らない（笑） |
| `branch` | `git branch` | ローカルブランチの一覧と現在のブランチを確認する | worktree中心になると使用頻度がかなり下がる |
