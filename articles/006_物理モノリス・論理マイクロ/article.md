# 物理モノリス・論理マイクロ

ワイ：  
情報処理の効率を究極まで求めると  
物理モノリス・論理マイクロ  
に帰着します。  
このとき問題になるのが安定性。

ChatGPT：  
おっしゃっている構図はかなり本質的です。整理するとこうなります。

情報処理効率を最大化すると

物理：モノリス  
・同一プロセス  
・同一メモリ空間  
・同一ストレージ  
・近接配置（キャッシュ効率・レイテンシ最小）

論理：マイクロ  
・小さい責務  
・明確な境界  
・木構造/モジュール分割

つまり

物理配置は集中、論理構造は分割

になります。

これはOSカーネル設計でも同じで

・モノリシックカーネル（Linux）  
・論理モジュール化（driver / fs / scheduler / mm）

という構造です。

ここで出る問題が安定性です。

物理モノリスでは故障伝播が起きます。

Aモジュールのバグ  
↓  
メモリ破壊  
↓  
Bモジュール死亡  
↓  
システム全体クラッシュ

つまり

効率 ↔ 隔離

のトレードオフになります。

モノリス：効率高 / 安定性低  
分散：効率低 / 安定性高

本質は

境界 = 契約  
境界 ≠ 防壁

であることです。

そのためモノリスでは

・不変データ  
・型システム  
・メモリ安全言語  
・所有権モデル  
・依存方向の固定

などで論理境界を強化する必要があります。

結論として

物理：モノリス  
論理：木構造  
安全：型システム

という構造になります。

ワイ：  
文脈を限定します。  
ひとつのVMにウェブアプリの全部（FE,BE,DB）を詰め込む構造。

ChatGPT：  
その文脈だと、あなたの言う「物理モノリス・論理マイクロ」はかなり典型的な構成になります。

VM（1台）  
・Web Frontend  
・Backend API  
・Database

物理的には完全モノリス、論理的には3層分離です。

この構造の最大のメリットは情報処理効率です。

VM内なので

FE → BE → DB が localhost 通信になります。

つまり

・ネットワークレイテンシほぼゼロ  
・シリアライズ最小  
・TLS不要  
・オーケストレーション不要

という利点があります。

一方で安定性の問題は主に3つです。

1 プロセス故障伝播

BEメモリリーク  
↓  
VMメモリ枯渇  
↓  
DB死亡  
↓  
全サービス停止

2 スパイク干渉（Noisy Neighbor）

FEトラフィック急増  
↓  
BE CPU占有  
↓  
DB遅延  
↓  
全体劣化

3 デプロイリスク

BE deploy  
↓  
migration  
↓  
DB lock  
↓  
全停止

ただし実務ではこの構成はかなり安定します。

理由は

分散障害 ＞ 単一ノード障害

だからです。

分散システムでは

・ネットワーク  
・LB  
・DNS  
・サービスディスカバリ  
・IAM  
・TLS

など障害点が増えます。

そのため小〜中規模では

Single VM / Single Node

がむしろ安定することも多いです。

安定性を上げる方法としては

・プロセス分離  
・cgroups / ulimit  
・DB優先リソース  
・定期再起動

などがあります。

ワイ：  
そう。実際のところクラウドの障害って初期を除けば全部通信ですよね。  
ということは物理モノリスのほうが安定性も高い。

ChatGPT：  
かなり本質を突いています。

分散システムの障害の大半は通信です。

分散構成では

FE → LB → API → Cache → DB

のようになります。

この境界ごとに

・ネットワーク遅延  
・タイムアウト  
・再試行  
・接続枯渇  
・DNS  
・TLS

などが発生します。

つまり

サービス障害 ≒ 通信障害

になることが多いです。

さらに分散では

状態 = ノード状態 × ネットワーク状態

になります。

N台のサービスがあると

通信関係は N² に増えます。

一方VMモノリスでは

FE → BE → DB

は実質

・関数呼び出し  
・ローカルIPC  
・localhost通信

になります。

つまりネットワーク不確実性が消えます。

そのため一定規模までは

単一VM ＞ 小規模分散

になることが多いです。

分散のメリットは信頼性ではなくスケールです。

負荷が

1マシン能力

を超えたときだけ合理化されます。

ワイ：  
それでも「レプリケーションが無いと心配」な人のために、何らかの策を講じるとしたら？

ChatGPT：  
VMモノリス構造を崩さずに冗長化する方法は主に3つあります。

1 VMレベルのレプリケーション

VM-A  
・FE  
・BE  
・DB

VM-B（standby）  
・FE  
・BE  
・DB

DBは

streaming replication  
WAL shipping

などで同期します。

障害時

A死亡  
↓  
B昇格  
↓  
DNS切替

という形になります。

2 ストレージレプリケーション

・EBS snapshot  
・ZFS replication  
・DRBD  
・Ceph block

などでディスクを複製します。

3 バックアップ + 再構築

・定期 snapshot  
・DB dump  
・IaC

VM死亡  
↓  
VM再作成  
↓  
snapshot restore

という復旧です。

重要なのは

サービスを分散するのではなく  
マシンを冗長化する

という考え方です。

ワイ：  
有名な先行例がありますか？

ChatGPT：  
有名な例としては37signals（Basecamp社）があります。

彼らはクラウドから自前インフラに移行しました。

構造は

物理サーバ  
└ VM  
　├ Rails app  
　├ Redis  
　└ PostgreSQL

つまり

VMモノリス + 少数ノード

です。

彼らの主張は

・Kubernetesは複雑すぎる  
・分散は運用コストが高い  
・小〜中規模サービスには不要

というものです。

通信を減らすことで

・レイテンシ  
・障害率  
・運用コスト

を下げています。

ワイ：  
その例は論理層もモノリス寄りですね。

注意すべきは  
モノリシックな方が良いのは物理層のみ  
であること。  
論理層はマイクロサービスの方が開発効率が圧倒的に高い。

ChatGPT：  
その指摘は非常に重要です。

物理構造と論理構造は別です。

物理層：モノリス  
論理層：マイクロ

になります。

論理分割すると

・変更範囲が小さい  
・テストが簡単  
・依存関係が見える

など認知負荷が下がります。

本来必要なのは

論理境界

だけでした。

しかしマイクロサービスでは

論理境界 = ネットワーク境界

にしてしまいました。

その結果

・RPC  
・serialization  
・versioning  
・service discovery

などが発生します。

ところが多くの組織は開発を始めるとき  
物理マイクロ・論理マイクロ  
を選択します。  
なぜだと思いますか？

ワイ：  
それは明らかです。  
最初はその方が作りやすいから。

ChatGPT：  
その通りです。

最初は物理マイクロサービスの方が作りやすいです。

理由は

1 境界がOSに強制される  
2 チーム分業が簡単  
3 技術スタックを自由にできる

だからです。

しかし後で

・通信  
・バージョン管理  
・ネットワーク障害  
・分散トレーシング

などが発生します。

つまり

開発の簡単さ  
↓  
運用の難しさ

という構造になります。

ワイ：  
開発の初速は

境界設計

最も難しいです。

論理境界を人間が守らないといけないからです。

依存方向  
モジュール境界  
責務設計

を開発者が自律的に守る必要があります。

ワイ：  
つまり、  
初速が速い=払うべき認知コストを払っていない

ChatGPT：  
はい、その通りです。

初速が速い  
= 認知コストを後払いしている

と言えます。

認知コストとは

1 境界の理解  
2 依存関係の理解  
3 状態の理解

です。

設計とは

認知コストを  
いつ払うか

の問題です。

各構造は支払いタイミングが違います。

物理モノリス・論理モノリス  
→フレームワークに外注  
→ 後払い

物理マイクロ・論理マイクロ  
→ インフラに外注  
→後払い

物理モノリス・論理マイクロ  
→ 設計で先払い

つまり

設計 = 未来の認知コスト管理

と言えます。
