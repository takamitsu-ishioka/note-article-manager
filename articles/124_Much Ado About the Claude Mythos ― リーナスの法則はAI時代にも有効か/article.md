## なぜELFでも可能なのか

ELFには以下の情報が含まれています。

- 機械語命令列
- 関数境界のヒント
- シンボル情報（残っていれば）
- 文字列
- ライブラリ呼び出し情報

例えば

```
char buf[64];
gets(buf);
```

が

```

lea rdi, [rsp]
call gets
```

になっていても、

「64バイトのバッファに gets()」

という危険なパターンは推測できます。

実際には

- Google の研究
- Microsoft の研究
- DARPA の研究

などで、LLMを逆アセンブル結果へ適用する試みが進んでいます。

## AIが苦手な脆弱性

ELF解析で難しいのは、

### 1. 状態遷移依存

```
login()
 ↓
init()
 ↓
privilege_check()
```

の3関数をまたいで成立する脆弱性。

人間のリバースエンジニアも苦労します。

---

### 2. ヒープ破壊

```
malloc
free
realloc
```

が複雑に絡むケース。

実行経路を追わないと分かりません。

---

### 3. レースコンディション

複数スレッドの相互作用。

これはLLM単体ではほぼ無理です。

---

## 実はAIより強いもの

脆弱性発見で現在最も成果を出しているのは

```
+

```

です。

例えば

- Google Project Zero
- Google DeepMind

などは、

AIに

> このELFで怪しい入力箇所を探せ

その結果をファザーへ渡しています。

つまり

```

↓

↓

```

という役割分担です。

---

もしあなたが扱っているのが組み込み機器やLinuxサーバ向け製品なら、

むしろ今後数年で大きく変わりそうなのは、「人間がソースを読む」工程より「人間がAIの見つけた候補を審査する」工程かもしれません。
