# Coding Agent: 「一発生成で全部うまくいくはず」という幻想

「一発生成で全部うまくいくはず」という幻想と、現場の現実

最近、こんな信念を持つ人に出会った。

「しっかり設計してAIにプロンプトを与えれば、一発でちゃんと動くコードが生成されるはずだ」

そしてその人は、私の仕事が遅いと思っているらしい。

一発生成は本当に成立するのか

結論から言うと、「条件付きで成立する」が正しい。要件が完全に閉じていて、例外が少なく、外部依存がなく、既存コードとの整合も不要。こういう世界なら一発でうまくいくことはある。

ただし現実の業務はだいたい逆だ。要件は揺れ、暗黙仕様があり、例外が後から出てきて、既存コードとの整合で詰まる。つまり「やってみないと分からないこと」が大量にある。

実際にやってみた結果

私は一発生成を実際に試した。結果は堂々巡り。生成すると微妙にズレ、修正プロンプトで別のズレが出て、また修正すると全体が崩れる。このループに入ると時間が溶ける。そこで戦略を変えた。

ボトムアップへの転換

今は小さく分解し、動く最小単位を作り、実装しながら仕様を確定させ、徐々に積み上げている。いわゆる「検証しながら進める」やり方だ。見た目は遅いが、実際は収束する。

「遅い」と見える理由

ここに認知のズレがある。一発生成派が見ているのは「コードが出るまでの時間（数分）」。現実で必要なのは「実際に動くまでの時間（数時間〜数日）」だ。さらにデバッグ、例外処理、既存コードとの調整、テストといった見えないコストがある。見えないものは存在しない扱いになる。その結果「自分ならもっと早くできるはず」という評価が生まれる。

その「根拠」は何か

多くの場合、それは限定的な成功体験、楽観的な前提、観測不足の組み合わせにすぎない。つまり事実ではなく仮説だ。

組織の幻想

これが厄介なのは個人で終わらないことだ。経営層やマネジメントが「ちゃんと設計すれば手戻りなしで作れる」と信じると、それが組織に広がる。一見正しそうだが、これは理想条件の一般化に近い。現実のソフトウェア開発は不確実性との戦いだ。

本来あるべき役割と現実

理想は、上が責務を定義し、権限を与え、任せること。しかし現実には不安、可視性の低さ、責任の重さによって「やり方への介入」が起きる。

現場で起きていること

結果として、手法に口出しされ、前提は共有されず、それでもスピードは要求される。現場の開発者は「仕事させろよ」と思う。

ではどうするか

理想を語るだけでは進まない。不確実な部分は実装で検証し、小さく進めて可視化し、完了までの時間で評価する。そして何より「一発でできるはず」という前提を疑うこと。

最後に

「遅い」と言われるとき、それは本当に遅いのか。それとも見えている範囲や前提が違うのか。現実と理想がズレているのか。この問いを持つだけで見え方は変わる。

そして今日も思う。めんどくさいな、と。でもそのめんどくささの中に、ちゃんと動くソフトウェアがある。
