# Tip 1：まず、いらないデータを消そう​  

一番簡単で、一番広く効く対策は何でしょうか。​  

私は、​  

> **いらなくなったデータを消す**

だと考えます。​  

たとえば、あなたが店を経営しているとします。​  

毎晩、売上金100万円を店のレジに入れたまま帰る店と、必要な小銭だけ残して売上金を銀行へ移す店。​  

泥棒に入られたとき、どちらの被害が大きいでしょう。​  

当然、100万円を置いてある店です。​  

コンピューターでも同じです。​  

10年前の顧客情報を持っていなければ、10年前の顧客情報は盗まれません。​  

退会した人の情報を消してあれば、その情報は漏れません。​  

使い終わった作業用ファイルを消してあれば、それも漏れません。​  

つまり、​  

> **持っていないデータは、絶対に盗まれない。**

これは当たり前すぎて見落とされがちですが、とても強力な性質です。​  

ファイアウォールは突破されるかもしれません。​  

パスワードは盗まれるかもしれません。​  

ソフトウェアには未知のバグがあるかもしれません。​  

人間は間違えます。​  

しかし、​  

**存在しないファイルを盗む方法はありません。**

### 今日できること​  

まず、こんなものを探してみましょう。​  

- 昔のCSV​  
- ダウンロードした顧客一覧​  
- 作業用にコピーしたデータ​  
- テスト用に作った本番データのコピー​  
- 退会した顧客のデータ​  
- 古いログ​  
- 「念のため」で何年も残しているバックアップ​  

そして考えます。​  

> 「これ、本当にまだ必要？」​  

必要でなければ消す。​  

必要なら、​  

> 「いつまで必要？」​  

を決めます。​  

できれば人間が定期的に掃除するのではなく、 **期限が来たら自動的に消えるようにします。**

# Tip 2：「全部入り金庫」を作らない​  

次に考えるのは、泥棒に入られたときの被害です。​  

銀行を想像してください。​  

100人のお客さんから預かったものを、一つの巨大な箱に全部入れる方法があります。​  

便利です。​  

箱は一つ。​  

鍵も一つ。​  

管理も簡単。​  

ところが、その鍵が盗まれたらどうなるでしょう。​  

**100人分、全部盗まれます。**

では、100個の箱に分けたら？​  

一つの鍵が盗まれても、盗まれるのは一箱です。​  

情報システムでも同じです。​  

たとえば100施設のデータを扱っているなら、​  

> 一つの認証情報で100施設全部を読める​  

という設計より、​  

> 施設Aの鍵では施設Aしか読めない  
> 施設Bの鍵では施設Bしか読めない​  

という設計のほうが、一回の事故の最大被害を小さくできます。​  

重要なのは、​  

**「侵入されないようにする」だけがセキュリティーではない**

ということです。​  

侵入される確率をゼロにはできません。​  

だったら、​  

> **侵入されても全部は取れない**

ようにすればいい。​  

船に水密区画があるのと同じです。​  

船体に一か所穴が開いたからといって、船全体が一気に水で満たされないようにします。​

# Tip 3：「マスターキー」を探して潰そう​  

100個に分ければ安全。​  

……とは限りません。​  

100個の部屋を作ったあと、​  

> 「管理人さんが大変だから」​  

という理由で、全室を開けられるマスターキーを一本作ったらどうでしょう。​  

結局、その一本を盗めば全部開きます。​  

コンピューターでは、こういう「マスターキー」が意外なところにあります。​  

たとえば、​  

- 全顧客を読める管理者アカウント​  
- 全データをまとめたバックアップ​  
- 全顧客データをコピーした分析用データベース​  
- 全データを検索できる検索インデックス​  
- 全顧客の情報が入ったログ​  
- 全環境に入れる共通パスワード​  

などです。​  

本番データベースを100個に分けたのに、バックアップでは100個を一つのファイルにまとめていた。​  

これでは意味がありません。​  

セキュリティーを考えるときには、​  

> **「全部を一度に読める道は残っていないか？」**

と聞いてみましょう。​  

一つでもあれば、そこが狙い目です。​

# Tip 4：「一度に運べる量」を人工的に作ろう​  

現実の泥棒には、面白い制約があります。​  

**重い。**

金塊が1万本あっても、一人で全部抱えて逃げることはできません。​  

トラックを持ってきたり、何往復もしたりする必要があります。​  

その間に見つかる可能性が高くなります。​  

ところがデータには重さがありません。​  

1件コピーするのと、100万件コピーするのとで、手間が100万倍になるわけではありません。​  

だったら、コンピューターの世界にも人工的に「重さ」を作ればいい。​  

たとえば、​  

> 一つのアカウントが1時間に読める個人情報は最大1,000件​  

という制限を作ります。​  

普段の仕事で一時間に10万件読む必要がないなら、大量に読もうとする動作はかなり怪しい。​  

100万件盗むには時間がかかります。​  

その間に止められるかもしれません。​  

つまり、​  

> **データにも重量制限を付ける。**

物理世界の安全性を、情報世界に人工的に持ち込むわけです。​

# Tip 5：鍵には寿命を付けよう​  

家の鍵を考えてください。​  

20年前にアルバイトをしていた人が、今でも店の鍵を持っている。​  

怖いですよね。​  

ところがコンピューターでは、似たことが普通に起きます。​  

昔作ったAPIキー。​  

昔発行したアクセストークン。​  

昔のプロジェクトで使ったパスワード。​  

退職した人が知っていた共有パスワード。​  

「まだ動いているから」という理由で、そのまま残っています。​  

ここで大事なのが **時間** です。​  

鍵を人ごとに分けるだけでは不十分です。​  

> **鍵を時間でも分ける。**

今日必要な鍵が、5年後にも使える必要はありません。​  

だから、​  

- 短い有効期限にする​  
- 定期的に交換する​  
- 退職・異動時には失効させる​  
- 管理者権限は必要なときだけ付ける​  
- 作業が終わったら権限を外す​  

ようにします。​  

これはデータにも同じことが言えます。​  

> 持っていられるから持つな。  
> **持たざるを得ない期間だけ持て。**

# Tip 6：パスワードをWikiに書かない​  

これはかなり具体的なTipsです。​  

社内Wikiや共有ドキュメントに、​  

> 本番DB  
> ID: admin  
> Password: XXXXXXXX​  

などと書いていませんか。​  

便利です。​  

そして、便利だから危険です。​  

みんなが見る場所に置けば、みんなが使えます。​  

さらに厄介なのは **履歴** です。​  

現在のページからパスワードを消しても、昔の版に残っている可能性があります。​  

だから、もし共有ドキュメントに認証情報を見つけたら、​  

1. 秘密情報専用の保管場所へ移す​  
2. 元ページから消す​  
3. **その認証情報自体を無効にする**
4. 新しい認証情報を発行する​  

ところまでやります。​  

3が重要です。​  

壁に書かれた合鍵の番号を黒く塗りつぶしても、誰かがすでに写真を撮っていたら意味がありません。​  

**鍵そのものを交換する必要があります。**

# Tip 8：木は林にまとめず、個々の木のまま森に隠せ​  

ここまでを一つの比喩でまとめてみましょう。​  

有名な言葉に、​  

> 木を隠すなら森の中​  

があります。​  

これを、セキュリティー向けに少し変えます。​  

> **木は林にまとめず、個々の木のまま森に隠せ。**

「木」は、データや鍵です。​  

「林」は、人間が便利だから作った集約場所です。​  

「森」は、世の中に存在する膨大なコンピューター、サービス、アカウント、データです。​  

100本の木を一か所へきれいに植えて、​  

> 「ここには重要な木が100本あります」​  

と看板を立てたら、泥棒には親切です。​  

100個の秘密を一つのサービスへ集める。​  

100顧客のデータを一つのDBへ集める。​  

全員の鍵を一つの共有ドキュメントへ集める。​  

全部同じ構造です。​  

**まとめられるから、まとめる。**

これをやめます。​  

共有しなくてもよいものは共有しない。​  

集約しなくてもよいものは集約しない。​  

同じ場所に置かなくてもよいものは同じ場所に置かない。​  

そして、​  

> **共有せざるを得ないものだけ共有する。**

# Tip 9：AIを「仕事の入口と出口」に置こう​  

ここからが、今すぐできる対策としてかなり面白いところです。​  

会社が、​  

> 「個人情報をどこへコピーしたか、必ず台帳に記録してください」​  

というルールを作ったとします。​  

たぶん、だんだん書かれなくなります。​  

なぜでしょう。​  

**面倒だからです。**

本来の仕事とは別に「台帳を書く」という仕事が増えるからです。​  

そこでAIを使います。​  

ルールを変えます。​  

> **仕事はAIに頼む。  
> またはAIと相談してから自分でやり、終わったらAIに報告する。**

これだけです。​  

たとえば、​  

「顧客Aのデータを調査したい」​  

とAIへ相談します。​  

AIと相談して、自分でCSVをダウンロードした。​  

終わったら、​  

「調査終了。CSVは削除した」​  

とAIへ報告します。​  

すると、​  

**仕事をした結果としてログが残ります。**

台帳を書くために仕事を止める必要がありません。​

# Tip 10：AIに「記録係」をやらせよう​
