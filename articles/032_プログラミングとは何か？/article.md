# プログラミングとは何か？

## プログラミングとは何か？

**  
ワイ：**

LLM生成AIのGUIをLLM生成AIにしてしまうのはどうでしょう？

例えば

ユーザー「対話の記録を全部消してね」

AI「期間の指定はありますか？」

ユーザー「無いよ。大昔のやつからさっきのやつまで全部」

AI「全期間のすべての対話ログを完全に削除します。復旧できませんが、よろしいですか？」

ユーザー「あ、ちょい待ち。昨日のやつは残して。」

AI「昨日と今日を除く全期間のすべての対話ログを完全に削除します。復旧できませんが、よろしいですか？」

ユーザー「よろ」

AI「削除しました」

**Gemini:**

そのアイデア、非常に面白いですね！まさに「CUI（Character User Interface）への回帰」でありながら、中身は超高性能な「自然言語によるGUI」という進化の形だと思います。

現在、多くのサービスが「設定画面（メニューやボタン）」を一生懸命作っていますが、それをすべて「対話」で置き換えてしまうという発想は、今後のAI活用における大きなトレンドの一つです。このアプローチには、学習コストがゼロになる「操作の民主化」や、複雑な条件指定が楽になるといったメリットがあります。

これを実現するには、LLMが会話から意図を抽出し、背後のAPIを叩く「Function Calling」という技術を使います。最終的には「言葉で伝えて、必要な分だけGUIを召喚する」というハイブリッドな形が標準になるかもしれません。

**ワイ：**

On-Demand Natural Language Programming

GUIはあってもいいけど上級者には不要かも。用途次第かな。

上級者には /bin/rm -rf * する自由が必要。

**Gemini:**

まさに、その通りですね。「On-Demand Natural Language Programming」という考え方は、コンピューティングのあり方を根本から変えるポテンシャルを持っています。

上級者が /bin/rm -rf * のような破壊的な操作を求めるのは、それが「最も速く、意図を正確に反映できる」からです。上級者向けのAIインターフェースは、単に結果を返すのではなく、「実行しようとしているコードを提示し、承認を求める」という、透過的なフローが理想的かもしれません。

最終的には、アプリケーションごとのGUIという概念が薄れ、「OS（システム）とどう対話するか」という一点に集約されるはずです。上級者にとっては、正規表現やパイプを書く代わりに、「自然言語で書かれた超高度なスクリプトをその場で生成・実行させる自由」こそが、新しい時代の武器になるのでしょう。

**ワイ：**

GUIとCUI(CLI)の本質的な違い：他のツールの部品になりにくい／なりやすい

**Gemini:**

まさに！その視点が「GUI vs CUI」の議論における最も鋭い本質ですね。GUIは人間がその場で完結させるための「終着駅」であるのに対し、CUIは「他のプログラムと繋がる」ための「ハブ」として設計されています。

CUIは標準入出力を通じて「疎結合」な部品になれますが、GUIはピクセルや独自のイベントループという「壁」があるため、他のツールから操作するのが困難です。

もしAIが「曖昧な人間の指示」を「厳密な構造化データ」に変換するハブとして機能すれば、このGUIの弱点は克服されます。「AIが生成した操作」を、そのまま別のツールにパイプで渡せるようになった時、初めて「AI-GUI」は真に実用的な「部品」になるのかもしれません。

**ワイ：**

On-Demand Natural Language Programming が普及すれば

業務を知っている人が自分でプログラムを書けるようになる。

「目的」と「手段」が一つの脳の中で直結する。

システム開発の効率が爆発的に上昇する。

**Gemini:**

そこが「ノーコード」が到達できなかった聖域ですよね。これまでの開発最大のボトルネックは、「業務のプロ」と「エンジニア」の間に横たわる「翻訳の壁」でした。

On-Demand Natural Language Programming はこのステップをスキップします。「一つの脳」で完結すれば、試行錯誤は高速化し、現場の微細なイレギュラーへの的中率も上がります。エンジニアを呼ぶまでもない「小さな非効率」が、爆発的な勢いで自動化されていくでしょう。

そうなると、エンジニアの仕事は「コードを書くこと」から、AIが生成するプログラムが走るための「安全で頑丈な土台（インフラ）」を設計することへシフトしていくはずです。  
  
プログラミングの哲学を持たない「業務のプロ」が作るコードはスパゲティになりがちかもしれませんが。

**ワイ：**

それでいいんじゃないでしょうか。業務ツールは使い捨てが基本で。

「大盛りスパゲッティ」は捨てればいい。

あ、AI に「モジュラリティを実現する形で再構成して」と言うと、できますか？

**Gemini:**

「業務ツールは使い捨て」という割り切り、非常に合理的です！AIによる「モジュラリティ（再構成）」は、むしろAIが最も得意とする領域の一つです。

AIに指示を出すことで、スパゲッティコードから共通処理を抜き出して独立した関数にしたり、抽象化したりといった「リファクタリング」が瞬時に行えます。これにより、「使い捨てツール」として現場で試行錯誤し、便利だとわかったものだけをAIに命じて「資産（モジュール）」へと昇華させるサイクルが生まれます。

「設計」という静的な作業が、「対話による継続的な改善」という動的なプロセスに変わる。そうなった時、文法を知っていることよりも、「問題をどう分解し、どういうモジュールがあれば美しいか」という設計思想（審美眼）を持っている人こそが、最強の「書き手」になるのかもしれません。
