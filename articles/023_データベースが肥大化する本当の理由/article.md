おそらく重要なのは、単なる「データの種類」ではなく、 **データが背負っている責任の違い** で保存先を分けることです。  

- **SSoT**  
  現在の正しい状態を表す。更新・整合性・バックアップ・移行に厳格さが必要。  
- **派生データ**  
  SSoTから再計算できる。検索速度や用途に合わせて自由に壊してよい。  
- **観測データ／履歴／ログ**  
  原則追記。大量保存、期間削除、圧縮、集計が重要。  
- **一時データ／キャッシュ**  
  消えてもよい。有効期限と再生成可能性が重要。  

たとえば、

| 責任 | 向いている保存先 |  
|---|---|  
| 顧客、患者、契約、設定などのSSoT | PostgreSQL |  
| センサー生データ、イベント履歴 | オブジェクトストレージまたは時系列DB |  
| 検索用インデックス | Elasticsearch系 |  
| キャッシュ、ジョブ状態 | Redis |  
| 分析用の集計・スナップショット | DWH、別DB、ファイル |  

という分離です。  

現在ありがちな問題は、 **一つのDBを万能な世界そのものとして扱う** ことです。すると、  

1. センサー大量書き込みの都合でSSoTの設計が歪む  
2. 検索や分析の都合でインデックスが肥大化する  
3. 古い観測データを消したいのに、業務データと絡んで消せない  
4. テスト時に全DBを再現しなければならない  
5. スキーマ変更が全用途へ波及する  

ということが起きます。  

逆にSSoTを小さく保てば、開発では「正しい状態を作る処理」と「用途別に複製・変換する処理」を分離できます。運用でも、障害時に守るべき対象が明確になります。  

ただし注意点もあります。保存先を分けると、今度は **データ間の同期** が問題になります。したがって原則は、  

> SSoTだけが事実を決定し、それ以外はSSoTまたは事実イベントから再構築できる。  

でしょうね。派生DBを人間や別サービスが直接更新し始めると、SSoTが複数に増殖して元に戻ります。  

要するにこれは「データベースを分ける」というより、  

> **真実を保存する場所と、真実を利用しやすく加工した場所を分ける**  

という設計です。  

そして実は、これは以前の「コード・データ・設定・ツール・説明をノードとするグラフ」という整理とも一致します。SSoTは根に近いノードで、それ以外はそこから生成される下流ノード。下流は捨てて再生成できるようにする。そうすると、整合性検査も開発もかなり単純になります。

- **設定項目を定義すること** は開発行為

- **現在の設定値** はイベントから導出された状態  

となります。

- どんなオプションが存在するか：開発  
- そのセンサーにどの値を適用したか：運用イベント  
- 現在有効な設定：導出状態

```text  
1. 事実

   → 追記専用  

2. 宣言  
   設定項目、制約、既定値、処理規則  
   → Git管理  

3. 現在状態  
   現在の注文状態、現在の設定、最新測定値  
   → 1と2から生成  
```

> **SSoTは、変更不能な事実とGit管理された規則である。  
> 現在状態は、その二つを計算した結果にすぎない。**  

かなり徹底した設計ですが、開発・テスト・復旧・監査は一気に単純になると思います。
