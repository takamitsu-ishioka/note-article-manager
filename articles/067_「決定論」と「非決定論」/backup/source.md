かなり面白い問いで、**「言葉を知っている」と「設計概念として使っている」の間に大きな谷がある**と思います。

私なら、一般的なソフトウェア開発者について、ざっくりこう推定します。

| レベル | できること | 推定割合 |
|---|---|---:|
| ① 単語を見たことがある | deterministic / non-deterministic を聞いたことがある | 70-90% |
| ② 意味を説明できる | 「同じ条件なら同じ結果になる」程度 | 50-70% |
| ③ 技術的に正確に扱える | 入力・状態・時刻・乱数・並行性などを含めて議論できる | 20-40% |
| ④ 設計原理として使う | 「ここは決定論的な層に閉じ込めよう」などと設計する | 10-20% |
| ⑤ システムを決定論/非決定論の境界として見る | 境界を意識して分離・検査・再現可能性を設計する | 数%〜10%程度 |

もちろん実測統計ではなく、開発者コミュニティ全般を見た場合の私の推定です。

特に面白いのは、**概念を知らずに決定論を使いまくっている人が非常に多い**ことです。

たとえば、

```text
pure function
immutable
reproducible build
idempotent
unit test
dependency injection
mock clock
random seed
event sourcing
```

などを使うとき、背後にはかなり頻繁に、

> 「入力を固定したら出力を固定したい」

という欲求があります。

つまり開発者は日常的に、

```text
f(x) = y
```

を欲しがっている。

ところが外部API、現在時刻、乱数、DB、ネットワーク、人間、LLMなどが入って、

```text
f(x, 世界の現在状態) = ???
```

になると困る。

そこで依存を注入したり、mockしたり、状態を隔離したりする。

これはかなりの部分、

**「非決定論的な世界との境界を外へ追い出し、内部を決定論的にしたい」**

という営みとして統一的に説明できます。

### ただし「deterministic」は分野によって認知度がかなり違う

コンパイラ、分散システム、データベース、組み込み、ゲーム、シミュレーション、暗号、テスト基盤あたりの人なら、かなり普通の語彙です。

一方、典型的なWeb業務アプリ開発者だと、

> deterministic？  
> ああ、同じ入力なら同じ出力になるやつですよね。

くらいまでは知っていても、

> この処理のどこまでが deterministic で、どこからが non-deterministic なのか？

とアーキテクチャを切るための軸として日常的に使っている人は、ぐっと減ると思います。

そして**生成AIが入ると、この概念の重要度が突然跳ね上がった**。

従来なら、

```text
入力
 ↓
プログラム
 ↓
出力
```

だったところへ、

```text
入力
 ↓
LLM
 ↓
出力
```

という巨大な非決定論的部品が普通に入ってきたからです。

だからAI Agent時代には、

```text
        ┌ deterministic ┐
入力 → 検証 → CLI/API → 保存
           ↑
        LLM / 人間
     non-deterministic
```

のように、**どこをAIに任せ、どこを決定論的コードとして固定するか**が設計上かなり重要になる。

これは、以前話していた「AIは部品メーカー」「deterministicな部分はスクリプト化する」というやり方そのものですね。

なので質問への短い答えなら、

> **「deterministic」という単語自体は、多くの開発者が知っている。しかし、それをソフトウェア設計を分割する基本軸として理解・使用している開発者はかなり少ない。生成AIによって、その古典的概念が急に重要になってきた。**

だと思います。

さらに面白いのは、**「決定論」という日本語にした瞬間、認知率が下がる可能性**があります（笑）。「deterministic test」は分かるのに、「この系は決定論的か？」と言われると突然哲学の授業っぽくなる。
