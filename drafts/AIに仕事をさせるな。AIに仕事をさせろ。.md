# AIに仕事をさせるな。AIに仕事をさせろ。

## Human searches → Agent searches → Nobody searches

会社で「AIエージェントの使いこなし術を紹介してほしい」と言われた。

おそらく求められているのは Tips & Tricks である。

- こういうプロンプトを書くとうまくいく
- こういうツールをAIに与えると便利
- コンテキストはこう管理する
- CLIと組み合わせると強い
- セッションはこう保存する

もちろん、そういう話もできる。

しかし困ったことに、私が提供したいものは Philosophy である（笑）。

なぜなら、個々のTipsを100個覚えるよりも、**Tipsを自分で生成できる原理を5個持った方が強い**からだ。

今日は、実際に私が朝から仕事をした過程を例に、その原理を考えてみたい。

---

# 1. 朝、仕事を始める

私の仕事環境はWindows上のWSLである。

朝、ターミナルを起動してWSLに入り、AIエージェントの新しいセッションを開始した。

```bash
$ wsl
$ agent_launch.sh new 'root session 2026-09-16'
```

そして最初に、こう聞いた。

> issue とチャットで、昨日朝から今までの間に、何か対応を必要とする動きがありましたか？

するとAIエージェントは、Issue Tracker、Gitリポジトリ、社内チャットを並行して調べ始めた。

しばらくして、だいたい次のような報告が返ってきた。

> **要対応の可能性が高いもの**
>
> 1. 社内チャットに、今日発生する可能性のある現場対応について連絡がある。
> 2. Gitリポジトリに、あなた宛てと思われるレビュー依頼が1件ある。
>
> **参考**
>
> Issue Trackerでは未完了だが、対応するGit issueはcloseされている、という状態不整合が9件ある。
>
> 自分のPRへの新規コメントはない。
>
> 担当issueにも大きな状態変化はない。

ここで重要なのは、AIが情報を見つけたことではない。

**私が情報を探していないこと**である。

---

# 2. 人間は情報システムの巡回者である必要があるのか

従来なら、おそらくこうなる。

```text
社内チャットを開く
    ↓
未読を探す
    ↓
Issue Trackerを開く
    ↓
担当チケットを見る
    ↓
GitのWeb画面を開く
    ↓
Notificationsを見る
    ↓
PRを見る
    ↓
「あれ、昨日何やってたっけ」
    ↓
メモを見る
```

人間が複数の情報システムを巡回して、

**「自分が今見るべきものは何か」**

を探している。

これは妙な話である。

人間が本当にやりたいのは、Issue Trackerを眺めることではない。

チャットをスクロールすることでもない。

GitのNotificationsを消化することでもない。

知りたいのは、

> **「何か私が判断すべきことはありますか？」**

である。

ならば、そう聞けばよい。

```text
Chat ─────┐
Issue ────┼─→ AI Agent ─→ 「今見るべきもの」を抽出
Git ──────┘
                         │
                         ↓
                      人間が判断
```

AIエージェントの第一の価値は、文章を書いてくれることではない。

**人間を情報システムの巡回業務から解放すること**である。

---

# 3. ただし、判断まで全部AIに渡すわけではない

先ほどAIは、現場対応に関するチャットを見つけた。

私はそれを読んで、こう判断した。

> これは別の担当者の仕事である。私に振られる可能性は低い。振られたらそのとき考えよう。

一方、レビュー依頼については、

> 私へのレビュー依頼なら、PRのページをブラウザで開いてください。

と指示した。

AIはブラウザを起動して該当PRを開いた。

そこで私は内容を確認し、

- Approve
- Merge
- Close

をWeb GUI上で行った。

ここが重要である。

AIエージェントを導入する目的は、

> **人間の操作をゼロにすること**

ではない。

私はむしろ、

> **人間が操作する場所を減らすこと**

だと考えている。

今回なら、

```text
レビュー対象を探す     → AI
PRページを開く         → AI
内容を読む             → 人間
Approveしてよいか判断  → 人間
Approve/Merge           → 人間
```

となる。

責任を伴う判断地点に到着するまでの移動をAIにやらせる。

人間は、判断すべき地点にだけ出現する。

GUIも同じである。

GUIを全廃する必要などない。

**GUIは、人間の判断が必要な地点にだけ存在すればよい。**

---

# 4. 「あとでやる」もAIに渡す

先ほどAIは、Issue TrackerとGit issueの状態不整合を9件発見していた。

これは急ぎではない。

そこで私は、

> その9件のURLをメモファイルに追記してください。

と指示した。

AIは9件について、

```text
Issue Tracker URL / Git issue URL
```

という形でローカルのMarkdownファイルへ追記した。

あとで私は、

```bash
$ vscode.sh ~/memo/raw.md
```

とした。

VS Code上ではURLをCtrl+Clickすれば、それぞれのページを開ける。

つまりAIに全部処理させたわけではない。

**「今やる必要はないが、後で人間が判断する仕事」を、人間が再発見しなくて済む状態にした**のである。

これは小さい違いに見える。

しかし実務では非常に大きい。

「あとでやろう」と思った仕事の最大の敵は、その仕事そのものではない。

**あとで、その仕事が何だったか思い出すこと**である。

---

# 5. 仕事を終えると、仕事そのものが文書になる

セッションを抜けたあと、AIエージェントのセッション一覧を取得した。

```bash
$ agent_session_list.sh json | json_pretty_print.sh | less
```

そこから先ほどのセッションIDを確認し、

```bash
$ agent_session_to_markdown.sh <session-id> > ./tmp/session_log.md
```

とした。

そして、

```bash
$ vscode.sh !$
```

で編集を開始した。

ちなみに `!$` はBashの履歴展開で、**直前のコマンドの最後の引数**を再利用する記法である。

つまりこの場合は実質、

```bash
$ vscode.sh ./tmp/session_log.md
```

である。

ここまで来ると面白い。

朝から私がやった仕事そのものが、ほぼそのままMarkdown文書になっている。

後から、

- Bash history
- 解説
- 補足
- 判断理由

を少し足せば、「AIエージェントをどう使って仕事をしたか」という教材になる。

つまり、

> **仕事をする**
>
> と
>
> **仕事を記録する**

が別の仕事ではなくなり始める。

---

# 6. ここまでは「Agent searches」の話である

この段階までを整理すると、従来はこうだった。

## Phase 1: Human searches

```text
人間
 ↓
Chatを探す
 ↓
Issue Trackerを探す
 ↓
Gitを探す
 ↓
メモを探す
 ↓
必要な情報を発見
 ↓
判断
```

AIエージェントを入れると、

## Phase 2: Agent searches

```text
Chat ───┐
Issue ──┼─→ Agent
Git ────┘
          ↓
   必要なものだけ報告
          ↓
        人間
          ↓
        判断
```

これはかなり便利である。

だが、午後になって私は別の問題に遭遇した。

そして、もう一段先があることに気づいた。

---

# 7. 午後、別の「情報探索地獄」に遭遇する

あるハードウェア連携機能について調べる必要があった。

ところが、そのために必要な情報が散らばっていた。

- 複数のGitリポジトリ
- リポジトリ外のドキュメント
- 開発環境
- 設定ファイル
- 特定メンバーの記憶
- 過去の個別コミュニケーション

こういう状態になると、典型的に二つの行動が発生する。

### パターンA

> とりあえず詳しい人に聞こう。

しかし詳しい人は忙しい。

返事が来ない。

返事が来る頃には、質問者の側が「何を聞きたかったんだっけ？」となる。

### パターンB

> 忙しそうだから自力で調べよう。

ところが、どこから調べればよいのか分からない。

何時間も探索する。

ようやく分かった頃には、

> 「ところで、この情報はどこに書いてあったんだっけ？」

となる。

これは個人の能力の問題ではない。

**構造の問題である。**

「もっと頑張って調べましょう」

「ちゃんとドキュメントを読みましょう」

「分からなかったら質問しましょう」

では解決しない。

---

# 8. では、この探索もAI Agentにやらせればいいのか

午前中の発想をそのまま適用すれば、

> 人間が探すのが大変ならAIに探させればいい。

となる。

確かに一歩前進である。

しかし、ここで疑問が生じた。

**なぜAIまで探さなければならないのか？**

人間が、

```text
Repository A
Repository B
Wiki
Chat
設定ファイル
詳しい人の記憶
```

を探索するのが苦痛だからAgentに探索させる。

だがAgentも結局、

```text
Repository A
Repository B
Wiki
Chat
設定ファイル
```

を探索している。

人間より速いだけで、問題構造は変わっていない。

ここで第三段階が見えてくる。

## Phase 3: Nobody searches

**そもそも、探索という仕事をなくせないか？**

---

# 9. 仕事とは「状態Aから状態Bへの変換」である

ここで私は、以前から考えていた原理を適用した。

> **仕事とは、状態Aから状態Bへの変換である。**

たとえばローカル開発環境の構築とは、

```text
状態A：
git cloneした直後。
何も動かない。

        ↓ Transformer

状態B：
必要な依存関係、設定、ツール等が揃い、
即座に開発・テストできる。
```

という変換である。

このとき、保存すべきものは何だろう？

状態Bそのものだろうか。

私は違うと思う。

**保存すべきは、状態Aを状態Bへ変換する規則である。**

つまりTransformerである。

---

# 10. ドキュメントではなくTransformerをGitに入れる

そこで考えた。

ローカル環境を最新の実行可能状態へ持っていく手順そのものを、MakefileとしてGit管理すればよい。

理想的には、新しく参加した人がやることは、

```bash
$ git clone ...
$ make build
```

だけになる。

もちろん途中で、人間にしかできない作業があるかもしれない。

たとえば、

- 秘密情報の入力
- 外部サービスへのログイン
- ブラウザ上での確認
- 実機の確認

などである。

ならば、その地点で止まればいい。

```text
make build
   ↓
自動処理
   ↓
自動処理
   ↓
「ここでブラウザにログインしてください」
   ↓
人間
   ↓
Enter
   ↓
自動処理再開
```

全部自動化する必要はない。

**どこで人間が必要になるかまで含めて、変換手順をコード化すればよい。**

---

# 11. MakefileにMakefileの仕事をさせる

ここでもう一つ重要なのは、巨大な初期化スクリプトを作らないことである。

たとえば、

```bash
initialize.sh
```

の中で、

```text
設定ファイルは変わった？
Python依存関係は変わった？
.NET依存関係は変わった？
コンテナ定義は変わった？
外部ツールは変わった？
```

などを自前で判定し始めると、初期化スクリプトそのものが巨大な状態管理システムになる。

しかしMakeには、もともと、

> prerequisiteがtargetより新しければrecipeを実行する

という仕組みがある。

ならば使えばいい。

```make
build: secrets dependencies containers tools

secrets: secrets-template
	./setup-secrets.sh

dependencies: dependency-definition
	./install-dependencies.sh
```

実際の構成はプロジェクトによって異なるだろうが、考え方は同じである。

**Makefileが既に持っている決定論的な仕事を、人間やAIが再実装しない。**

各recipeも、小さな単一責務のスクリプトか、単純な1行コマンドにする。

ここには重要な原則がある。

> **AIにコードを書かせる前に、そのコードを書く必要があるのかを疑え。**

---

# 12. Human searches → Agent searches → Nobody searches

ここで、今日一日の出来事が一本につながった。

午前中、私は複数の情報システムを巡回する仕事をAI Agentへ渡した。

```text
Human searches
      ↓
Agent searches
```

午後、別の探索問題に遭遇した。

そこで、

> Agentに探索させればよい

と思った。

しかし、もう一歩考えた。

> **Agentすら探索しなくて済むようにできないか？**

結果として、

```text
Human searches
      ↓
Agent searches
      ↓
Nobody searches
```

という三段階が見えてきた。

これが、私が考えるAIエージェント活用の成熟モデルである。

---

# 13. AIに仕事をさせることがゴールではない

AI活用の話をすると、

> これをAIにやらせよう。

という話になりやすい。

私は、それだけでは不十分だと思う。

人間が毎日3時間かけている仕事をAIが30秒でやってくれた。

素晴らしい。

だが次に問うべきなのは、

> **その30秒の仕事、本当に必要なのか？**

である。

AIによってコストが100分の1になったからといって、無駄な仕事が有益な仕事に変わるわけではない。

むしろAIが安価であるからこそ、無意味な処理を大量に増殖させる危険すらある。

したがって、

> 人間の仕事をAIへ移す

だけではなく、

> AIへ移した仕事そのものを消せないか考える

必要がある。

だから私はこう言いたい。

> **AIエージェント活用の最終形は、AIエージェントに仕事をさせることではない。**
>
> **AIエージェントにさえ、その仕事をさせなくて済む系を作ることである。**

---

# 14. 決定論と非決定論を分ける

この考え方をもう少し一般化すると、仕事には大きく二種類ある。

### 決定論的な仕事

同じ状態に対して、基本的に同じ処理をしてほしいもの。

たとえば、

- ファイルをコピーする
- URLを生成する
- 依存関係をインストールする
- 状態を比較する
- ログを保存する
- ブラウザを指定ページで開く
- 更新された依存関係だけ再構築する

こういう仕事は、できるだけプログラム、CLI、Make、Gitなどの決定論的な系へ落とす。

### 非決定論的な仕事

入力だけでは正解が一意に決まらないもの。

たとえば、

- この連絡は重要か
- 今対応すべきか
- この問題とあの問題は同じ原因ではないか
- 何から調べるべきか
- そもそも現在の業務構造がおかしいのではないか

こういう領域では、LLMが強い。

さらに、その外側に人間がいる。

- 本当にApproveしてよいか
- このリスクを取るか
- 誰が責任を持つか
- この仕事自体をやめるべきか

最終的な責任を伴う判断である。

したがって構造は、

```text
決定論的な道具
      ↓
非決定論的なAI
      ↓
責任主体としての人間
```

となる。

ただしこれは単純な三層構造ではない。

実際には、

```text
決定論
 ↓
AI
 ↓
決定論
 ↓
AI
 ↓
人間
```

のように組み合わせればよい。

重要なのは、

> **毎回考えなくてよいことを、毎回AIに考えさせない**

ことである。

---

# 15. AIトークンを倹約するとは、AIを使わないことである

AIの利用料を減らそうとすると、

- プロンプトを短くする
- 小さいモデルを使う
- キャッシュする
- 出力トークンを減らす

といったTipsが出てくる。

もちろん全部有効である。

しかし最強のトークン節約法はもっと単純である。

> **決定論的に解ける問題についてAIに聞かない。**

たとえば、

> このファイルは前回から更新されていますか？

をLLMに毎回判断させる必要はない。

Makeに聞けばよい。

> このIssueのURLを開いて。

なら、LLMがブラウザ操作を推論する必要もない。

```bash
issue_open.sh 123
```

という道具があればよい。

AIはその道具を呼べばよい。

AIは万能機械として使うより、

**非決定論的な判断が必要な場所に限定して使った方が強い。**

AIに仕事をさせる。

そして、その仕事の中から決定論的な部分を見つけたら、AIから仕事を奪う。

これを繰り返す。

するとAIの仕事は徐々に、

> **本当に考えなければならないこと**

へ濃縮されていく。

---

# 16. そして会議も同じではないか

ここまで考えると、別のものが気になってくる。

**会議である。**

たとえば週次会議で、

- 一週間何をしたか報告する
- Issueの状態を確認する
- PRの状況を確認する
- 困っていることを列挙する
- 次週の予定を話す

ということをしているとする。

しかし、作業そのものがセッションログとして残り、

Issue Tracker、Git、ChatなどをAgentが横断し、

必要な変化だけが人間へ届くようになったらどうなるか。

会議で、

> 「今週は○○をしました」

と報告する必要はあるのだろうか。

みんな、もう知っている。

すると理想的には、誰かが言い始める。

> 「……この週次会議、要らないのでは？」

ここで私は、

> 会議を廃止せよ！

と言いたいわけではない。

むしろ逆である。

**会議が担っている機能を、一つずつ会議の外へ出せばよい。**

```text
進捗共有 → 非同期
状態確認 → Agent
記録     → 自動
定型確認 → CLI/API
```

そうすると最後に、

> **複数の人間が同時に存在しなければ成立しない仕事**

だけが同期コミュニケーションとして残る。

---

# 17. 非同期革命のあとに残る同期コミュニケーション

私は今のところ、同期コミュニケーションとして最後まで残るものを三つに分類している。

## 1. 救急

待てない。

遅延そのものに大きな損失がある。

> 「あとで読んで返事します」

では困る。

同期の価値は**低レイテンシ**である。

## 2. 政治

情報共有だけでは終わらない。

利害や価値観や責任を持つ複数主体が、互いの反応を見ながら落とし所を作る必要がある。

同期の価値は**相互作用による意思決定**である。

## 3. 雑談（別名、ブレスト）

何を話すべきかすら事前に分からない。

Aの発言がBを刺激する。

Bの発言がCを刺激する。

そして最初には誰も持っていなかったDが生まれる。

同期の価値は**創発**である。

圧縮するとこうなる。

> **同期が必要なのは、待てないとき、決められないとき、何が出るか分からないとき。**

逆に問いたくなる。

```text
緊急ではない。
その場で何も決めない。
創発も求めていない。

        ↓

では、なぜ全員を同時刻に集めた？
```

---

# 18. 理想のPhase 1

だから私が密かに期待している未来は、会議全廃ではない。

まずPhase 1として、PMがこう宣言することである。

> **「週次会議を廃止し、週次雑談会を開催します。」**

（笑）

これは名前を変えただけに見えて、実は大きな変化である。

旧来の週次会議は、

```text
情報収集
 ↓
進捗報告
 ↓
状況共有
 ↓
問題発見
 ↓
意思決定
 ↓
ついでに雑談
```

だった。

それが、

```text
情報収集 ─┐
進捗把握 ─┼→ 非同期系
問題発見 ─┘

意思決定 → 必要な人だけ同期

雑談     → 週次雑談会
```

になる。

機械に構造化可能なコミュニケーションを渡した結果、

**人間には非構造的コミュニケーションが残る。**

これはむしろ健全なのではないか。

そしてPhase 2。

> 「週次雑談会は、話題がなければ参加自由にします。」

Phase 3。

> 「今週、誰も来ませんでした。」

Phase 4。

> **「雑談したくなったら雑談しましょう。」**

定例という概念が消える（笑）。

非同期革命とは、会議をなくす運動ではない。

> **同期という高価な資源を、本当に同期性を必要とする仕事へ返還する運動**

なのである。

# 19. 難攻不落の要塞をどう攻略するか

ここまで来ると、業務改善に対する考え方そのものが変わってくる。

複雑な業務に遭遇すると、普通はその複雑性を攻略しようとする。

- ドキュメントを整備する
- 詳しい人を育てる
- 手順書を書く
- 情報共有を徹底する
- AIに全部読ませる
- AIに全部覚えさせる

いわば、難攻不落の要塞へ正面攻撃を仕掛ける。

しかし別の攻略法がある。

> **要塞の内部を攻略しない。**
>
> **要塞に入る必要そのものを消す。**

情報探索が大変なら、Agentに探索させる。

Agentの探索も大変なら、情報を構造化する。

構造化された手順の同期が大変なら、状態変換そのものをTransformerとしてGitへ置く。

そして最終的に、

```bash
git clone
make build
```

に近づける。

つまり、

> **複雑性を理解して征服するのではなく、複雑性との接触面を消す。**

のである。

難攻不落の要塞は、攻略しなくてよい。

**要塞を要らなくすればよい。**

# 20. Tips & Tricksを教えるな。Tips & Tricksを教えろ。

さて。

私は会社から、

> AIエージェントの使いこなし術を紹介してください。

と言われた。

たぶん期待されているのはTips & Tricksである。

だからTipsも紹介する。

- AIに複数システムを横断させる
- ブラウザを開く小さなCLIを作る
- セッションログを保存する
- Markdown化する
- `!$` で直前の引数を再利用する
- Makefileで依存関係を管理する
- 小さな単一責務スクリプトをAIに与える

全部便利である。

しかし、本当に伝えたいのはそこではない。

なぜそのTipsが生まれたのか。

その背後にある原理である。

> **人間は判断に集中する。**

> **決定論的な仕事を非決定論的なAIにやらせ続けない。**

> **結果ではなくTransformerを保存する。**

> **人間が探しているものはAgentに探させる。**

> **Agentが探しているものは、誰も探さなくてよい構造にする。**

> **同期という高価な資源は、同期でしかできない仕事に使う。**

個々のTipsは陳腐化する。

ツールも変わる。

今日のAIエージェントも、数年後には別の何かになっているだろう。

しかし原理があれば、新しいTipsを自分で生成できる。

だから、

> **Tipsを100個覚えるより、Tipsを生成する原理を5個持て。**

これが、私の考える「AIエージェント使いこなし術」である。

そして最も重要なTipsを最後にもう一度書いておく。

> **AIに仕事をさせるな。**
>
> **AIに仕事をさせろ。**
>
> **そして、その仕事をAIから奪え。**

Human searches.

Agent searches.

Nobody searches.

そこまで行って初めて、AIによる業務改善は一周するのだと思う。
